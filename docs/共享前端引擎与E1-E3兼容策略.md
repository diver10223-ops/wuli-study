# 共享前端引擎与E1—E3兼容策略

## 目标

将重复的本地存储、诊断渲染、评分和重置逻辑提取为共享引擎，使E4—E8主要编写物理内容配置，而不是复制整页JavaScript。

## 本轮范围

1. `assets/storage.js`统一安全读取、写入、删除和导出；
2. `assets/diagnostic.js`统一选择题诊断、关键门槛、猜对门槛、薄弱节点和结果保存；
3. `data/e4-a-diagnostic.js`保存E4 A轨15题及通过规则；
4. E4 A诊断作为第一项迁移验证。

## 对E1—E3的影响

本轮对E1—E3是**零迁移、向后兼容**：

- 不修改任何E1—E3页面；
- 不修改既有`localStorage`键名；
- 不转换或删除已有学习记录；
- 不改变A/B/C通过分数和门槛；
- 新引擎使用普通全局脚本，不要求打包工具或服务器。

后续迁移E1—E3时必须逐页进行“旧结果与新结果同输入对比”。只有题目数量、分数、分项、门槛、存储键和返回路线全部一致，才替换旧实现。旧数据模式如需升级，必须读取旧版本并显式迁移，不能静默丢弃。

## 风险控制

1. 引擎加载失败时抛出明确错误，不产生伪成绩；
2. 损坏的本地JSON返回默认值，不阻断页面；
3. 配置保留原存储键`physics-e4-a-diagnostic-v1`，迁移前后记录兼容；
4. 自动审计同时检查外部引擎、数据文件语法、配置题数与关键门槛；
5. E1—E3仍由现有结构审计保护，暂不承担新引擎试验风险。

## 下一步

完成共享学习任务引擎和考试引擎；先用于E4 A轨知识卡、模型和基础卷。稳定后再评估是否迁移E1—E3，不为“代码统一”强制重写已经可用的页面。
